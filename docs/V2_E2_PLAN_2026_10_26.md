Frozen before E2 measurements, 2026-10-26 03:52 UTC. Time budget ends approximately 05:21 UTC.

Research target: RQ1/H1 in the V2 proposal: CPU tiering benefits depend on reusable conversational histories leaving GPU KV, rather than KV budget alone. RQ0 screens already fail the B5 gate. No adaptive scheduler will be implemented without new mechanism evidence.

1. Run the existing 30-request, two-conversation P-QA interleaved 2 QPS trace on B1 at 8 GiB as a capacity gate. Capture outputs, actual prompt counts, errors, memory and cache counters. Do not interpret overload as a clean latency comparison.
2. Freeze two-conversation P-QA traces at 0.2 QPS, exponential arrivals, seeds 17/29/43, 15 questions per conversation, identical content and 64-token output budget. Evaluate B1/B2 at 4 and 8 GiB. Use balanced arm order across seeds; full service restart before each arm, empty-cache reset and identical warmup. These are independent cold-start run replicates, not same-engine crossovers (B1/B2 have different connector configurations). CPU L1 fixed at 16 GiB. No targeted cache eviction or artificially timed late revisit. Record GPU fit versus pressure using model KV bytes/token and actual cache counters. If capacity gate or first screen requires a design change, record it before subsequent runs.
3. A useful tiering result requires reduced recomputation, external cache hits/CPU reads, and lower arrival TTFT, with failures reported. GPU-fit runs control connector overhead. Report per-run p50/p95/p99 and throughput; no sample-level pseudo-replication. Three seeds support exploratory run-level uncertainty only, not population claims.
4. If feasible, run existing P-SESSION dev trace under B1/B2 as a separately labelled adaptation. Preserve original evidence-visible checkpoint protocol.
5. Audit prompt/server-token identity and output hashes across paired runs, save text privately. Hash mismatches do not establish quality preservation. Any QA score needs a fixed cited evaluator; do not call output agreement a LoCoMo quality score.
6. Deliver reproducible commands, compact tracked summaries, plots/table generation, limitations, and append a clearly separate V2 section to main_results. Preserve V1 artifacts.
